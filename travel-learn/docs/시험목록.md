# 실기기 시험 목록

자동 시험(PC)으로 확인한 것은 `README.md`의 검증 현황에 있다. 이 문서는 **실제 폰과 실제 보드에서만 확인할 수 있는 것**이다.
결과 칸에 날짜와 ○/×를 적고, ×면 앱의 "이벤트 기록 > 공유"로 기록을 남긴다.

## 준비

| 준비물 | 내용 |
|---|---|
| 폰 | Galaxy S26 Ultra, 앱 설치, `Android17_제약과_초기설정.md` 4장의 설정 완료(모든 줄 ✓) |
| 현관판 대역 | 처음에는 PC의 `tools/virtual_board.py`, 그다음 실제 UNO R4 WiFi + 예제 `VirtualBoard` |
| 같은 Wi-Fi | 폰과 현관판(또는 PC)이 같은 공유기 2.4 GHz에 연결. PC는 방화벽에서 8080 허용 |
| 확인 수단 | 앱 화면의 "이벤트 기록", 현관판 콘솔(직렬 모니터) 출력 |
| 선택 | PC에 adb가 있으면 Doze 강제 진입 가능: `adb shell dumpsys deviceidle force-idle` / 해제 `unforce` |

출발 신호 보내는 법: 가상 현관판 콘솔에서 `depart 1`, 실제 보드 예제에서는 직렬 모니터에 `d 1`.

## E. 통신 실패

| 번호 | 절차 | 기대 결과 | 결과 |
|---|---|---|---|
| E-1 | 폰의 Wi-Fi를 끄고 `depart 1` | 현관판: 약 1초 간격 재시도, 45초 뒤 포기. 폰: 아무 일도 없음 | |
| E-2 | `depart 1` 직후(5초 안에) Wi-Fi 켜기 | 재시도 중 전달. 폰 기록의 "경과 ...ms"가 실제 지연과 비슷함 | |
| E-3 | 가상 현관판을 `--drop-trips 2`로 띄우고 기록 1건 동기화 | 폰: 전송 실패 2회 뒤 5초·15초 간격으로 다시 보내 "저장 완료". 통계에는 1회만 반영 | |
| E-4 | `--bad-mac-trips 1`로 같은 시험 | 폰: "응답 MAC 불일치"로 실패 처리 후 재전송. 현관판은 두 번째를 `dup`으로 처리 | |
| E-5 | `--busy-trips 1`로 같은 시험 | 503 뒤 재전송 성공 | |
| E-6 | 측정이 끝난 뒤 현관판 전원을 끈 채 귀가(Wi-Fi 연결) | 기록이 "[미전송]"으로 남음. 현관판을 켜면 다음 재시도 때(최대 약 5분, 절전 지연은 실측) 전송 | |
| E-7 | 동기화 도중 현관판 전원 뽑기(실제 보드) | 다시 켠 뒤 폰이 재전송. 통계 표본 수가 정확히 1만 증가 | |
| E-8 | 현관판을 껐다 켠 직후 hello 없이 `d 1` | 전달됨(폰 주소가 EEPROM에 남아 있음) | |
| E-9 | 공유기에서 폰 IP가 바뀌게 한 뒤(Wi-Fi 껐다 켜기) `depart 1` | 폰이 새 주소로 hello를 다시 보내 전달됨 | |
| E-10 | 폰을 다른 Wi-Fi(예: 핫스팟)에 연결 | "현관판 미확인" 상태. 오류가 반복해서 쌓이지 않음 | |
| E-11 | 모바일 데이터를 켠 채 집 Wi-Fi 연결(인터넷이 안 되는 공유기면 더 좋음) | hello·동기화가 Wi-Fi로 나감 | |
| E-12 | 같은 출발 신호를 두 번 받게 함(가상 현관판에서 폰 응답 전에 재전송되도록 `--delay-ms` 없이 Wi-Fi가 약한 곳에서 시험) | 폰 기록에 "출발 신호 중복", 측정은 1건 | |

## G. 실제 보드 (UNO R4 WiFi)

| 번호 | 절차 | 기대 결과 | 결과 |
|---|---|---|---|
| G-1 | Arduino IDE에서 예제 `VirtualBoard` 컴파일·업로드 | 오류 없음. 스케치 크기를 적어 둠(예상 약 80 KB) | |
| G-2 | 직렬 모니터에서 IP 확인, PC의 `tools/virtual_phone.py --board <IP>:8080` 실행 | hello 성공. `d 1` → 폰 대역이 측정 → 저장 → `s`로 통계 확인 | |
| G-3 | `virtual_phone.py --ignore-departs 3` | 보드가 재전송해 4번째에 전달. 직렬 모니터가 멈추는 시간을 체감으로 기록 | |
| G-4 | 폰 대역을 끈 채 `d 1` | 45초 동안 재시도 후 포기 표시. 그동안 `loop()`가 한 번에 얼마나 멈추는지 `millis()` 차이로 측정(예상 약 1.2초) | |
| G-5 | 기록 저장 순간의 멈춤 시간 측정(`onTripStored` 전후 `millis()`) | 수치를 적어 둠(예상 0.1~0.3초) | |
| G-6 | 기록 10건 저장 후 전원 뽑았다 켜기 | `s` 출력이 그대로. 부팅 횟수 +1 | |
| G-7 | 저장 도중(직렬에 저장 표시가 뜨는 순간) 전원 뽑기 10회 | 다시 켰을 때 통계가 초기화되지 않음(이전 값 또는 새 값) | |
| G-8 | `EEPROM.length()` 출력 | 8192 | |
| G-9 | 메인 프로그램(`entrance-board/SmartEntrance`, 실제 조회 모드. HTTP로 날씨·교통 API 호출)과 합친 뒤 G-2 반복 | API 호출과 출발 신호·동기화가 서로 막지 않음(조회 한 건은 최대 8초, 그 사이 폰 요청은 재전송으로 처리). 소켓 부족 오류 없음 | |
| G-10 | 24시간 연속 가동 후 `d 1`, 동기화 | 정상 동작. `p`로 폰 온라인 표시 확인 | |
| G-11 | 실제 폰 앱과 G-2 흐름 전체 | 0장의 기본 흐름이 실제 보드로도 통과 | |
| G-12 | 폰에 미전송 기록 1건을 남긴 채 현관판 EEPROM을 초기화(배치 변경 펌웨어 업로드 등) → 귀가 동기화 → 그 뒤 새 외출 2건 | 새 외출 2건이 모두 `applied:1`로 반영됨(`dup`으로 버려지지 않음) | |

## H. 통합 (현관판 완성 후)

| 번호 | 절차 | 기대 결과 | 결과 |
|---|---|---|---|
| H-1 | RFID 태그 → 문 열기 → 걸어서 정류장 → 귀가 | 사람이 폰을 한 번도 만지지 않고 기록 1건이 통계에 반영 | |

| H-3 | 태그 없이 문만 열기 | 출발 신호가 나가지 않음(메인 프로그램 판단) | |
| H-4 | 태그 후 문 열고 곧바로 다시 태그(취소) | 폰 측정이 '현관판에서 취소'로 끝나고, 현관판은 그 사람의 정보를 다시 보여 주며 새 출발을 감시 | |
| H-5 | 화면의 "지금 출발/여유 있음" 표시와 실제 버스 탑승 여부를 5회 비교 | 여유 시간 0 이상일 때 실제로 탑승 가능 | |
| H-6 | 정보 화면 오른쪽 아래 확인: 폰 대기 중 / 폰 Wi-Fi 끈 채 출발 신호 포기 뒤 / 현관판을 켠 직후 | 각각 `PHONE OK` / `PHONE --` / 폰이 hello를 보내기 전까지 `PHONE --` | |
| H-7 | 태그 직후 화면이 LOADING인 동안 문을 열고 2~3초 안에 닫기 | 현재 조회 한 건만 끝낸 뒤 "HAVE A NICE DAY", 나머지 조회 중단. `age_ms`와 폰 출발 시각이 문 열림 시각을 반영 | |
| H-8 | 폰이 귀가 동기화를 보내는 순간에 맞춰 카드 태그(조회 중) | 동기화가 시간 초과로 한 번 실패해도 폰 재전송으로 "저장 완료". 통계 표본 수가 정확히 1 증가 | |
| H-9 | API 서버가 느릴 때(휴대폰 핫스팟 등 느린 망) 태그 | 요청 한 건이 8초를 넘지 않고 화면이 표시되거나 NO DATA. 그동안 문 센서가 동작 | |
| H-10 | 공유기 전원을 껐다 켬(현관판은 켠 채) | 끊긴 지 약 30초 뒤 시리얼에 `WiFi lost, reconnecting`, 공유기 복구 뒤 전원 재시작 없이 API 조회·폰 hello·동기화·출발 신호가 다시 됨 | |
| H-11 | 지금 강수 없음 + 2~3시간 뒤 비 예보인 날 출발 | 다이얼·화면은 RAIN, 시리얼의 `[travel] departure ... wx=0` (학습은 강수 없음 칸) | |
| H-12 | 외출 직후 돌아와 문을 연 채 다시 태그(취소) → 문 닫기 → 다시 문을 열고 나가기 | 문을 닫아도 출발 신호가 나가지 않음. 다시 문을 열고 나가면 출발 신호 전달 | |
| H-13 | 같은 카드를 5초 안에 두 번 태그 → 5초 뒤 다시 태그 | 두 번째는 무시(LOADING 없음). 5초 뒤 태그하면 다시 조회 | |

## I. 리뷰 수정 회귀 확인

| 번호 | 절차 | 기대 결과 | 결과 |
|---|---|---|---|
| I-1 | 미전송 0건·최초 설치 상태에서 현관판을 끄고 대기 시작, Wi-Fi를 유지한 채 보드 켜기 | 5초·15초·60초·이후 5분 간격 등록 재시도로 연결. 출발 수신 가능 | |
| I-2 | 외부 인터넷 또는 API만 막고 로컬 Wi-Fi 유지, 태그 후 문 열기 | 날씨·교통 실패와 무관하게 출발 신호 전달 | |
| I-3 | 1·2번 정류장 설정, GPS 불가 상태에서 알림 도착 → 2번 선택 | 2번 기록·통계만 증가. 선택 중 머문 시간은 이동 시간에 추가되지 않음 | |

| I-5 | 정류장 두 곳의 조회 사이에 의도적으로 지연 추가 | 첫 정류장 ETA는 두 번째 조회에 걸린 시간만큼 감소 | |
