# 통계·통신 모듈의 메모리 사용량 (Arduino UNO R4 WiFi)

보드 자원: RAM 32 KB, 플래시 256 KB, EEPROM(데이터 플래시) 8 KB.

## 1. 요약

| 항목 | 모듈이 쓰는 양 | 보드 전체 대비 | 근거 |
|---|---|---|---|
| RAM(고정) | 3,640바이트 | 11% | 실제 코어로 링크해 측정 |
| RAM(일시, 힙) | 1,024바이트 | 힙 8 KB 중 | EEPROM 기록 순간에만. 코어 소스로 확인 |
| 스택(모듈 함수) | 최대 약 600바이트 | 메인 스택 예약 1 KB | 함수별 측정값을 호출 순서대로 합산 |
| 플래시 | 약 13.5 KB | 5% | 실제 코어로 링크해 측정 |
| EEPROM | 4,096바이트(0~4095번지) | 50% | 배치 계산 + 호스트 시험 |

측정 방법: 공식 코어 소스(ArduinoCore-renesas)와 ARM GCC로 모듈·예제를 컴파일하고 링크해 `arm-none-eabi-size`로 읽었다(`arduino/TravelLearn/extras/realcore/build_real.sh`).
공식 빌드는 GCC 7.2.1, 여기서는 GCC 13.2를 썼으므로 수백 바이트 차이가 날 수 있다. **실제 보드에 올려서 재지는 않았다.**

## 2. RAM

### 2.1 링크 결과 (사용자 4명, 정류장 4곳 기본 설정)

| 스케치 | 플래시(text) | data | bss |
|---|---|---|---|
| 기준(Wi-Fi 서버·클라이언트·EEPROM만 사용, 모듈 없음) | 61,312 | 544 | 15,588 |
| 기준 + TravelLearn 전 기능 | 74,816 | 544 | 19,180 |
| 차이 = 모듈 | **+13,504** | 0 | **+3,592** |
| 예제 VirtualBoard | 80,620 | 544 | 19,236 |
| 예제 BasicIntegration | 72,304 | 544 | 19,180 |

bss에는 코어가 잡아 두는 힙 8,192바이트와 메인 스택 1,024바이트가 들어 있다.
VirtualBoard 기준으로 고정 사용량은 19,780바이트이고 남는 RAM은 약 13 KB다. 메인 프로그램(화면·센서·API 응답 해석)이 이 안에서 움직여야 한다.

### 2.2 모듈 안의 내역

`TravelLearn` 객체 하나가 3,468바이트, HMAC 작업 공간이 172바이트다.

| 구성 | 바이트 | 식 |
|---|---|---|
| 통계·주소·중복 목록의 RAM 사본(EEPROM 이미지) | 1,336 | 20 + 41·U + 72·U·S |
| 요청 버퍼(메서드·경로·MAC·본문 480) | 590 | 고정 |
| 응답 본문 버퍼 | 481 | 고정 |
| 송신 조립 버퍼 | 768 | 고정 |
| 출발 신호 대기 표 | 96 | 24·U |
| 공유 키 | 64 | 16·U |
| 초기 설정값 표(초) | 32 | 2·U·S |
| 서버 객체, 플래그, 시각, 콜백 등 | 101 | |
| HMAC 작업 공간(전역) | 172 | 고정 |
| 합계 | 3,640 | |

U = `TL_MAX_USERS`, S = `TL_MAX_STOPS`. 통계 한 칸은 6바이트(표본 수 1, 연속 이상값 횟수 1, 평균 2, 표준편차 2)이고 사용자·정류장 한 쌍마다 날씨 3 × 시간대 4 = 12칸이다.

| 설정 | 통계 칸 수 | 이미지 | `TravelLearn` 객체 | EEPROM 사용 |
|---|---|---|---|---|
| U=4, S=4 (기본) | 192 | 1,336 | 3,468 | 4,096 (2벌 × 2블록) |
| U=2, S=2 | 48 | 390 | 2,416 | 2,048 (2벌 × 1블록) |

2명·2곳으로 줄이면 RAM 1,052바이트, EEPROM 2,048바이트가 줄어든다(`TlConfig.h`의 세 값을 고친다. 크기를 바꾸면 저장된 통계는 초기화된다).

### 2.3 스택과 힙

- 모듈 함수의 스택 사용(ARM, -Os, `-fstack-usage` 측정값을 호출 순서대로 더함)
  - 출발 신호 전송: `loop` 8 → `sendOne` 24 → `attemptDepart` 40 → `postToPhone` 248 → MAC 계산 56+48+24 → `sha256Block` 152 = **600**
  - 요청 수신·인증: `loop` 8 → `serveOne` 96 → `handleRequest` 80 → `checkAuth` 104 → MAC 계산 128 → `sha256Block` 152 = **568**
  - 기록 저장: 8 + 96 + 80 + `handleTrips` 128 + `commit` 72 + `slotCrc` 72 = **456**
- 여기에 WiFiS3·EEPROM 라이브러리 내부와 `snprintf`가 쓰는 스택이 더해진다. 이 부분은 재지 못했다.
- 코어 설정상 메인 스택 예약은 1,024바이트(`BSP_CFG_STACK_MAIN_BYTES`), 힙은 8,192바이트다. 메인 프로그램에서 `tl.loop()`를 깊은 함수 안쪽이 아니라 `loop()`에서 직접 부르는 것이 안전하다.
- EEPROM에 쓸 때 코어가 1,024바이트 블록 버퍼를 힙에 잠깐 잡는다. 모듈 자체는 동적 할당을 하지 않는다.

## 3. EEPROM

UNO R4의 EEPROM 라이브러리는 1바이트만 바꿔도 그 바이트가 속한 **1,024바이트 블록 전체를 지우고 다시 쓴다**(코어 소스 `virtualEEPROM.cpp`, `EEPROM.h`로 확인).
쓰는 도중 전원이 끊기면 블록 전체가 깨질 수 있으므로, 전체 상태를 이미지 하나로 묶어 두 벌(A/B)을 번갈아 쓴다. 읽을 때는 CRC가 맞는 벌 중 순번이 큰 쪽을 쓴다.

### 3.1 배치 (기본 설정, 한 벌 기준)

| 영역 | 오프셋 | 크기 | 내용 |
|---|---|---|---|
| 머리말 | 0 | 16 | 식별자 `TLS1`, 배치 버전, 표 크기, 부팅 횟수, 순번 |
| 폰 주소 | 16 | 32 | 사용자 4명 × (IP 4, 포트 2, 플래그 2) |
| 중복 방지 목록 | 48 | 132 | 사용자 4명 × (이동 ID 8개 × 4 + 위치 1) |
| 통계 칸 | 180 | 1,152 | 192칸 × 6 |
| CRC-32 | 1,332 | 4 | |
| 합계 | | 1,336 | 블록 단위로 올림 → 한 벌 2,048 |

A벌 0~2047번지, B벌 2048~4095번지. 4096번지 이후는 건드리지 않는다(호스트 시험으로 확인).

### 3.2 쓰기 횟수와 수명

| 사건 | EEPROM 기록 | 블록 지우기 |
|---|---|---|
| 이동 기록 1건 반영 | 1회(한 벌 = 2블록) | 블록당 0.5회 |
| 부팅 | 1회(부팅 횟수 저장) | 블록당 0.5회 |
| 폰 주소가 바뀐 hello | 1회 | 블록당 0.5회 |
| 주소가 같은 hello, 통계 조회, 여유 시간 계산 | 없음 | 0 |

호스트 시험에서 기록 100건 뒤 블록당 지우기 횟수는 49~50회였다.
하루에 기록 4건, 부팅 1회, 주소 변경 1회로 잡으면 블록당 하루 3회다. 데이터 플래시 보증 수명 100,000회(RA4M1 데이터시트 최솟값) 기준으로 약 90년에 해당한다.

### 3.3 걸리는 시간

기록 1회는 2블록 지우기 + 2,048바이트 쓰기다. RA4M1 데이터시트의 대표값으로 계산하면 약 0.1~0.2초, 최댓값으로 계산하면 2초 이상도 가능하다. **실제 보드에서 재지 않았다.** 이 동안 `tl.loop()`가 멈추며, 폰은 응답을 5초까지 기다린다.

## 4. 전원 차단 시험 (호스트)

기록 1건을 반영하는 동안의 쓰기 단계 2,051곳(지우기 2 + 바이트 쓰기 2,048 + 완료 후) 각각에서 전원을 끊어 보았다.

| 재부팅 후 상태 | 횟수 |
|---|---|
| 이전 상태 그대로(기록 미반영) | 1,338 |
| 새 상태 완성(기록 반영) | 713 |
| 깨진 상태 | 0 |

모든 경우에 폰이 같은 기록을 다시 보내면 정확히 한 번만 반영됐고, "저장 완료" 응답은 실제 저장 뒤에만 나갔다.
한계: 호스트 모형은 "지우는 중 끊기면 블록이 0xFF, 쓰는 중 끊기면 뒷부분이 0xFF"로 가정한다. 실제 플래시는 끊긴 순간의 비트가 불확정일 수 있는데, 그 경우에도 CRC 불일치로 걸러지도록 설계했다. 실제 보드에서 전원을 뽑는 시험은 하지 않았다.
