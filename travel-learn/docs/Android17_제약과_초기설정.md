# Android 17 / One UI 9에서 "앱을 열지 않고 상시 대기 → 출발 신호로 측정 시작"이 가능한가

대상: Galaxy S26 Ultra, Android 17(API 37), One UI 9. 조사일 2026-11-12.
표시: **[문서]** 공식 문서에서 확인, **[소스]** 공개 소스 코드에서 확인, **[미검증]** 실기기에서 확인해야 함.

## 1. 결론

가능하다. 단, 아래 세 가지를 사용자가 한 번 설정해야 하고, 그중 하나라도 빠지면 "자동"이 "알림을 눌러야 시작"으로 떨어진다.

| 필요한 설정 | 없을 때 일어나는 일 |
|---|---|
| 위치 권한 **항상 허용** | 화면이 꺼진 상태에서 위치 측정을 스스로 시작하지 못한다. 앱은 출발 알림을 띄우고 사용자가 누르면 측정한다 |
| **로컬 네트워크**(근처 기기) 권한 | 현관판의 출발 신호를 받지 못하고, 귀가 후 동기화도 안 된다 |
| 배터리 **제한 없음** + 삼성 절전 예외 | 밤새 대기하다 Doze에 들어가면 출발 신호를 놓칠 수 있고, 서비스가 죽은 뒤 스스로 되살아나지 못할 수 있다 |

추가 하드웨어는 필요 없다(6장).

## 2. 공식 문서로 확인한 것과 설계 반영

### 2.1 포그라운드 서비스 유형

| 확인한 내용 | 설계 |
|---|---|
| **[문서]** `connectedDevice` 유형은 네트워크 등으로 외부 기기와 상호작용하는 용도다. 매니페스트에 `FOREGROUND_SERVICE_CONNECTED_DEVICE`와, `CHANGE_NETWORK_STATE` 등 지정된 권한 중 하나를 선언해야 한다. 시간 제한은 문서에 없다 | 대기 서비스의 유형으로 사용. `CHANGE_NETWORK_STATE` 선언 |
| **[문서]** `location` 유형은 위치 서비스가 켜져 있고 위치 권한이 있어야 한다 | 측정 중에만 이 유형을 더한다 |
| **[문서]** `location` 유형 서비스는 앱이 백그라운드일 때 만들 수 없다. `ACCESS_BACKGROUND_LOCATION`이 있으면 예외다 | **통신 서비스가 실행 중이라는 이유로 위치를 켤 수 있다고 가정하지 않았다.** 출발 신호를 받으면 권한 상태를 먼저 확인하고, "항상 허용"일 때만 자동 시작한다 |
| **[문서]** Android 14 이상 대상 앱이 백그라운드에서 while-in-use 유형 서비스를 만들면 즉시 `SecurityException`이 난다 | `startForeground` 호출을 예외 처리로 감싸고, 실패하면 알림으로 사용자 확인을 요청한다 |
| **[문서]** `dataSync` 유형은 Android 15부터 하루 6시간 제한과 부팅 시 시작 금지가 있다 | 상시 대기에 `dataSync`를 쓰지 않는다 |

### 2.2 백그라운드에서 서비스 시작

| 확인한 내용 | 설계 |
|---|---|
| **[문서]** 백그라운드에서 포그라운드 서비스를 시작하면 `ForegroundServiceStartNotAllowedException`이 난다(Android 12 이상 대상) | 서비스는 앱 화면에서 "대기 시작"을 눌러 시작하고 계속 유지한다 |
| **[문서]** 예외: `BOOT_COMPLETED`·`MY_PACKAGE_REPLACED` 수신 직후, 사용자가 배터리 최적화를 끈 앱, 알림 조작, 화면에 보이는 액티비티 | 재부팅 후 `BOOT_COMPLETED`에서 `connectedDevice` 유형으로 다시 시작. 배터리 "제한 없음"을 초기 설정에 포함해, 서비스가 죽었을 때 60분 주기 알람으로 되살릴 수 있게 함 |
| **[문서]** Android 15 이상 대상 앱은 `BOOT_COMPLETED`에서 일부 유형(dataSync, camera, mediaPlayback, phoneCall, mediaProjection, microphone)을 시작할 수 없다 | 부팅 때는 목록에 없는 `connectedDevice`만 시작한다. 위치 유형은 부팅 때 더하지 않는다 |

### 2.3 로컬 네트워크 권한

| 확인한 내용 | 설계 |
|---|---|
| **[문서]** Android 17에서 대상 SDK 37 이상인 앱은 `ACCESS_LOCAL_NETWORK` 권한(근처 기기 그룹, 사용자에게 묻는 런타임 권한)이 있어야 집 안 주소와 통신할 수 있다 | 매니페스트에 선언, 초기 설정 화면에서 요청 |
| **[문서]** 나가는 TCP뿐 아니라 **들어오는 TCP 연결을 받는 것**도 이 권한이 필요하다 | 출발 신호 수신(폰이 서버) 경로가 이 권한에 걸린다는 점을 설정 화면과 시험 목록에 반영 |
| **[문서]** 권한이 없으면 TCP는 보통 시간 초과로 실패한다 | "연결 시험" 버튼의 실패 안내에 이 권한 확인을 넣음 |
| **[문서]** 대상 SDK 36 이하 앱은 Android 17에서 임시로 암묵 허용된다 | 권한 문제로 막히면 `targetSdk`를 36으로 낮춰 빌드하는 우회가 가능하다(`app/build.gradle` 한 줄) |
| 문서는 백그라운드·포그라운드 서비스에서의 동작 차이를 언급하지 않는다 | **[미검증]** 화면이 꺼진 상태에서 서버 소켓이 계속 연결을 받는지 실기기 확인 필요 |

### 2.4 절전(Doze)

| 확인한 내용 | 설계 |
|---|---|
| **[문서]** Doze 중에는 네트워크 접근이 중단되고 wake lock이 무시된다 | |
| **[문서]** 배터리 최적화에서 제외된 앱은 Doze 중에도 네트워크를 쓰고 부분 wake lock을 잡을 수 있다 | 초기 설정에서 배터리 "제한 없음"을 요청. 출발 신호 처리 중 20초, 측정 중 최대 측정 시간 + 1분 동안만 wake lock을 잡는다 |
| **[문서]** 문서는 포그라운드 서비스가 Doze 제한에서 면제된다고 쓰지 않는다 | 포그라운드 서비스만으로 충분하다고 가정하지 않고 배터리 제외를 필수 설정으로 둠 |
| **[문서]** 강제 Doze 시험: `adb shell dumpsys deviceidle force-idle`, 해제 `unforce` | 시험 목록에 포함 |

### 2.5 위치

| 확인한 내용 | 설계 |
|---|---|
| **[문서]** 백그라운드 위치는 포그라운드 위치를 먼저 허용받은 뒤 따로 요청해야 하고, Android 11 이상에서는 설정 화면에서 사용자가 "항상 허용"을 고른다 | 설정 화면에 "위치" → "위치 항상 허용" 두 단계 버튼 |
| 대기 중 위치 요청 금지(요구 사항) | 대기 중에는 `requestLocationUpdates`를 부르지 않는다. 측정 시작 때 요청하고 도착·취소·시간 초과 때 해제한다. 이벤트 기록에 "위치 측정 시작/중단"이 남는다 |

### 2.6 삼성 One UI

| 확인한 내용 | 출처 구분 |
|---|---|
| "초절전 상태 앱"은 백그라운드에서 전혀 실행되지 않는다. 한동안 쓰지 않은 앱은 자동으로 절전 상태가 된다(삼성 개발자 문서 기준 약 3일, 초절전은 16일. 바뀔 수 있음) | 삼성 공식 |
| One UI 6 이상에서는 Android 14 대상 앱의 포그라운드 서비스가 Android 정책대로 동작하도록 했다 | 삼성 공식 |
| "자동 절전 예외 앱"에 넣으면 자동 절전 대상에서 빠진다 | 삼성 공식(한국어 지원 페이지) |
| Wi-Fi > 지능형 Wi-Fi의 "모바일 데이터로 전환", "Wi-Fi 절전 모드" 항목 | 삼성 공식. 화면이 꺼졌을 때 Wi-Fi 연결 유지 여부는 문서에 없음 **[미검증]** |
| 최근 앱에서 밀어 닫을 때 포그라운드 서비스가 죽는지 | 공식 자료 없음 **[미검증]** |
| One UI 9(Android 17)의 S26 Ultra 배포 | 언론 보도로만 확인(2026년 9월 한국부터). 삼성 공식 날짜는 찾지 못함 |

## 3. 동작 구조

```
[대기]   포그라운드 서비스(connectedDevice) · 서버 소켓 8765 열림 · 위치 요청 없음 · wake lock 없음
            │  현관판 → POST /v1/depart
            ▼
[수신]   wake lock 20초 · 이동 ID 중복 확인 · 문 열림 시점 = 수신 시각 − age_ms
            │
            ├─ 위치 "항상 허용" + 위치 켜짐 → startForeground(connectedDevice | location) → 위치 요청 시작  → 응답 "tracking"
            └─ 아니면 → 알림 "출발 신호를 받았습니다" (누르면 앱 화면이 뜨고 그때 측정 시작)                 → 응답 "noperm"
            ▼
[측정]   GPS 2초 간격 · Wi-Fi 끊김 = 집을 떠남 · 정류장 반경 진입 2회 연속 → 도착
            │  도착 / 수동 도착 / 취소 / 시간 초과
            ▼
[저장]   기록을 DB에 저장 · 위치 요청 해제 · 유형을 connectedDevice로 복귀
            │  집 Wi-Fi 재연결 → hello 성공
            ▼
[동기화] 미전송 기록을 이동 ID 순으로 전송 · stored:1 받은 것만 완료 표시
```

## 4. 초기 설정 (한 번만)

앱 화면 "1. 초기 설정"의 버튼 순서와 같다. 각 줄 앞의 ✓/✗로 상태를 확인한다.

1. **알림** 허용. 출발·도착 알림과 "도착/취소" 버튼에 필요하다.
2. **위치** 허용. "정확한 위치"로, "앱 사용 중에만 허용"을 고른다.
3. **위치 항상 허용**. 버튼을 누르면 설정 화면이 열린다. "항상 허용"을 고른다.
4. **로컬 네트워크**(근처 기기) 허용.
5. **배터리 제한 없음**. 뜨는 창에서 허용한다. 안 뜨면 "앱 설정 열기" > 배터리 > 제한 없음.
6. 삼성 설정 > 배터리 > 백그라운드 사용 제한에서 이 앱을 **자동 절전 예외 앱**에 추가한다(메뉴 이름은 One UI 버전에 따라 조금 다르다). "사용하지 않는 앱을 절전 상태로 전환"이 켜져 있어도 예외 앱은 빠진다.
7. 삼성 설정 > 연결 > Wi-Fi > ⋮ > 지능형 Wi-Fi에서 **모바일 데이터로 전환**을 끈다. 켜 두면 집 Wi-Fi가 약할 때 통신이 집 밖 망으로 빠져 현관판과 연결되지 않을 수 있다.
8. 공유기에서 **현관판 IP를 고정(DHCP 예약)** 한다. 폰 IP는 고정하지 않아도 된다(폰이 주소가 바뀔 때마다 현관판에 알린다).
9. 앱 "2. 현관판 연결"에 사용자 번호, 현관판 IP, 공유 키를 넣고 "연결 시험".
10. "3. 정류장"에 좌표를 넣는다. 정류장에 서서 "현재 위치"를 누르면 채워진다.
11. "대기 시작".

## 5. 한계

- **강제 종료**: 설정에서 앱을 "강제 종료"하면 사용자가 앱을 다시 열 때까지 아무것도 실행되지 않는다. 재부팅해도 되살아나지 않는다. Android의 정상 동작이며 우회할 수 없다.
- **재부팅 직후**: 화면 잠금을 한 번 풀기 전에는 대기가 시작되지 않는다.
- **출발 신호를 받을 수 있는 시간**: 문이 열린 뒤 폰이 집 Wi-Fi 범위를 벗어나기 전(보통 수십 초)까지다. 현관판은 45초 동안 약 1초 간격으로 다시 보낸다. 이 안에 못 받으면 그 외출은 측정되지 않는다.
- **깊은 절전에서 첫 신호 지연**: 폰이 깊이 잠든 상태에서는 첫 연결이 늦거나 실패할 수 있다. 재전송으로 보완하며, 늦게 받아도 `age_ms`로 문 열림 시점을 보정한다 **[미검증: 실제 지연 크기]**.
- **권한 재설정**: 앱을 몇 달 쓰지 않으면 Android가 권한을 자동 회수할 수 있다. 시스템 업데이트 뒤 삼성 절전 설정이 초기화됐다는 사용자 보고도 있다(커뮤니티 자료).
- **위치 오차**: 건물 사이·지하에서는 GPS 오차가 커진다. 오차 50 m 초과 위치는 근처에 20초 이상 머물러야 도착으로 보고(품질 1), 쓸 만한 위치가 90초 동안 없으면 알림으로 수동 확인을 요청한다(품질 2). 지하철역처럼 도착 지점이 지하인 정류장은 좌표를 **출입구**로 잡는다.
- **도착 시각 편향**: 반경(기본 30 m)에 들어선 순간을 도착으로 보므로 실제 정류장 표지 앞보다 수 초~20초 이르다. 매번 같은 방향의 오차라 통계와 여유 시간 계산에는 일관되게 반영된다.
- **다른 Wi-Fi**: 집이 아닌 Wi-Fi에 붙어도 앱은 설정된 현관판 주소로 hello를 한 번 시도한다. 내용은 사용자 번호와 폰 IP뿐이고 응답 MAC이 맞지 않으면 무시한다.
- **평문 통신**: 위조·변조는 막지만 같은 Wi-Fi 안에서 엿보는 것은 막지 못한다. 위치 좌표는 망으로 나가지 않는다.
- **백그라운드 위치 알림**: Android가 "이 앱이 백그라운드에서 위치를 사용했습니다"라는 안내를 가끔 띄울 수 있다.

## 6. 추가 하드웨어 (부품 신청 세션 전달 사항)

- 이 기능(폰 통신·학습) 때문에 **새로 필요한 부품은 없다.** UNO R4 WiFi의 내장 Wi-Fi와 내장 EEPROM만 쓴다. 별도 GPS·RTC·SD 카드 모듈 불필요.
- 전제 하나: "문 열림 감지"가 초기 계획서의 부품(RC522, PIR, DHT11, 서보)만으로는 안 된다. 문 열림 센서(자석식 리드 스위치, 예: MC-38)가 신청 목록에 있는지 센서 담당 세션이 확인해야 한다. PIR로 대신하면 "문이 열린 순간"이 아니라 "현관 앞 움직임"이 기준이 되어 측정 시작점이 흔들린다.
- 검토했다가 제외한 것: BLE로 출발 신호 보내기. UNO R4 WiFi는 안테나를 공유해서 Wi-Fi와 BLE를 동시에 쓸 수 없다(Arduino 공식 문서). 메인 프로그램이 날씨·교통 API 때문에 Wi-Fi를 계속 써야 하므로 BLE는 쓰지 않는다. 실기기 시험에서 Wi-Fi 수신이 끝내 불안정하면 그때 외장 BLE 모듈(HM-10 계열)을 예비안으로 검토한다. 지금 신청할 필요는 없다.

| APK가 S26 Ultra에 설치·실행되는지 | 빌드·서명·정렬 검사만 통과 |
| 백그라운드에서 `location` 유형 추가가 "항상 허용"으로 실제 허용되는지 | 공식 문서 문장 + 실패 시 대체 경로 구현 |
| 화면 꺼짐·Doze 상태에서 서버 소켓이 출발 신호를 받는지, 지연은 얼마인지 | 문서상 배터리 제외 앱은 네트워크 사용 가능 |
| 로컬 네트워크 권한이 백그라운드 서비스에서도 유지되는지 | 문서에 언급 없음 |
| 밤샘 대기 후에도 서비스가 살아 있는지, 배터리 소모 | 없음 |
| 최근 앱에서 밀어 닫았을 때 서비스 유지 여부 | 없음 |
| 실제 GPS 궤적에서의 도착 판정 | 모의 궤적 200회(잡음 4 m) 시험만 통과 |
