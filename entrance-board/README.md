## RAM 사용량 (이동 시간 모듈과 합친 상태, 2026-11-13 다시 계산)

재는 방법: 공식 UNO R4 코어 소스(ArduinoCore-renesas)와 ARM GCC 13.2로 스케치·라이브러리 전체를 컴파일·링크하고 `arm-none-eabi-size -A`로 읽었다.
Arduino IDE는 GCC 7.2.1을 쓰므로 수백 바이트 다를 수 있다. **실제 보드에서 잰 값이 아니다.**

| 구역 (바이트) | 데모 모드 | 실제 조회 + TravelLearn |
| --- | --- | --- |
| 플래시 (`.text`+`.data`) | 75,648 (29%) | 106,288 (41%) |
| 전역 변수 (`.data`+`.bss`, IDE가 "전역 변수"로 보여 주는 값) | 9,792 (30%) | 14,220 (43%) |
| ㄴ 그중 TravelLearn(`tl` 객체 3,468 + HMAC 작업 공간 172) | 0 | 3,640 |
| ㄴ 그중 스택에서 옮긴 조회 버퍼와 출발 이벤트 | 68 | 684 |
| 힙으로 쓸 수 있는 구역 (코어가 잡아 두는 8,192 포함) | 21,664 | 17,240 |
| 메인 스택 예약 | 1,024 | 1,024 |
| 기타 (`.noinit` 28, 인터럽트 벡터 표 256, 정렬 여백) | 288 | 284 |
| 합계 | 32,768 | 32,768 |

- 예전 README의 "10,804바이트(코어가 잡는 힙 8,192와 스택 1,024 포함)"는 틀렸다. IDE가 보여 주는 전역 변수 값에는 힙과 스택이 들어 있지 않다.
- 힙은 8,192바이트에서 끝나지 않는다. 코어의 `_sbrk`는 전역 변수 바로 뒤부터 스택 예약 바로 아래(`__HeapLimit`)까지 늘어난다.
- Wi-Fi 연결 하나마다 수신 버퍼 1,024바이트, EEPROM 기록 순간에 1,024바이트를 힙에서 잡는다. 실제 힙 최고 사용량은 재지 않았다.

### 메인 스택 (1,024바이트)

- 코어 설정 `BSP_CFG_STACK_MAIN_BYTES` = 0x400. 스케치에서 바꿀 수 없다.
- 시작 코드(FSP `SystemInit`)가 스택 포인터 감시를 켜지만, Arduino 코어의 `arduino_main()`이 `setup()` 전에 끈다(`cores/arduino/main.cpp`).
  그래서 1,024바이트를 넘어도 보드가 바로 멈추지 않고, 넘친 만큼 힙 구역 맨 위를 쓴다. 힙은 아래에서부터 올라오므로 둘이 만나면 아무 경고 없이 값이 깨진다.
- 함수별 스택(`-fstack-usage`)을 호출 관계(`-fcallgraph-info`)를 따라 더한 최악값. 가상 함수 호출은 들어갈 수 있는 함수 중 가장 깊은 것으로, 소스가 없는 `snprintf`(약 400)·`vsnprintf`(약 390)는 역어셈블해서 셌다. 인터럽트가 겹치면 수십~200바이트가 더 든다(재지 않음).

| 가장 깊은 경로 (바이트) | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 조회: `loop` → `handleCard` → `fetchWeather`/`fetchArrival` → WiFiClient 읽기 → 모뎀 명령(`vsnprintf`) | 1,396 | 900 |
| 화면: `loop` → `drawRows` → `screenInfoRow` → `snprintf` | 756 | 676 |
| 이동 시간 모듈: `loop` → `travelLoop` → 출발 신호 전송 → WiFiClient 읽기 → `vsnprintf` | 1,316 | 1,236 |
| 조회 사이의 이동 시간 모듈: `loop` → `handleCard` → `betweenFetches` → (위와 같음) | 없음 | 1,284 |

- 고친 것: `Net.cpp`의 큰 버퍼(요청 경로 `reqPath[320]`, 키·값 `fieldName`·`fieldText`)를 세 조회 함수가 같이 쓰는 static 버퍼로, 버스·지하철 한 건의 값과 `sendDeparture()`의 `DepartureEvent`를 static으로 옮겼다. `fetchBus` 프레임 560 → `fetchArrival`에 합쳐져 96, `fetchWeather` 488 → 144, `loop` 120 → 40.
- 남은 것: WiFiS3는 소켓을 연결하거나 읽을 때마다 그 아래에서 약 500~600바이트를 쓴다(모뎀 명령 문자열을 `vsnprintf`로 만든다). TravelLearn은 그 위에 약 600바이트를 더 쌓아 모듈 혼자 최악 1,196바이트다. `tl.loop()`를 `loop()` 맨 위에서 불러도 1,024를 넘는다.
  TravelLearn을 고쳐도(MAC 버퍼·줄 버퍼를 전역으로) 약 950바이트까지만 줄어 1,024 안에 여유 있게 넣기 어려워서, 이번에는 라이브러리를 고치지 않았다.
- 지금 빌드에서 힙 구역은 17,240바이트이고 넘치는 스택은 최대 약 260바이트(+인터럽트)라, 힙이 16KB 가까이 쌓이지 않는 한 만나지 않는다. 힙 최고 사용량은 수 KB로 추정하지만 **실제 보드에서 재지 않았다(미확인)**.

## 이동 시간 모듈과의 연결

`../travel-learn/arduino/TravelLearn`이 실제 모듈이고, `SmartEntrance/travel_link.cpp`가 메인 코드의 약속(`travel_iface.h` v0.2)을 이 모듈로 바꿔 부른다. 값은 아래처럼 바꾼다.

추가로 바뀐 점

- `travel_iface.h`에 `travelOnCancel`(출발 후 90초 안에 같은 사람이 다시 태그하면 외출 취소, 화면에 TRIP CANCELED), `travelPhoneOnline`, `hostWeatherPty`를 더했다.
- `config.h`의 `Stop`에 `walkSec`(학습 기록이 없을 때의 예상 이동 시간)을 더했다.
- 정류장·사용자 번호는 `STOPS`·`USERS` 배열 위치+1이다(`Stop.key`가 아님). 폰 앱의 정류장 n번은 `STOPS`의 n번째와 같아야 하고, 학습을 시작한 뒤에는 순서를 바꾸지 않는다. 바꾸면 기록이 섞인다.
- 출발 신호의 정류장은 0(모름)으로 보낸다. 폰이 그 사용자의 정류장을 모두 감시한다.
- 시간대는 보드 시각(`WiFi.getTime()`)으로 정하고, 없으면 폰이 hello로 알려 준 시각을 쓴다.
- 전달 결과와 기록 저장은 시리얼 모니터에 `[travel]`로 찍힌다. 정보 화면 오른쪽 아래에 그 사람의 폰 연결 여부(`PHONE OK` / `PHONE --`)가 보인다.
- 학습에 넘기는 날씨는 가장 가까운 예보 시각의 강수형태(`WeatherInfo.nowPty`)다. 다이얼과 화면의 `NEXT 3H`는 앞으로 3시간 기준 그대로다.

| 메인 코드의 값 | TravelLearn에 넘길 값 |
| --- | --- |
| `userId` (0부터) | `user` = `userId + 1` (1~4) |
| 정류장 키 (`STOPS` 배열의 위치) | `stop` = 배열 위치 + 1 (1~4) |
| 가장 가까운 예보 시각의 기상청 PTY 코드(`nowPty`) | `wx` = `TravelLearn::wxFromPty(pty)` |
| 현재 시각 (한국 시) | `tb` = `TravelLearn::tbFromHour(hour)`, 시각을 모르면 255 |
| 첫 차량 도착까지 남은 초 | `etaS`, 모르면 -1 |
| 출발 당시 외부 기온 | `tempC`, 모르면 -128 |

| 메인 코드의 함수 | 부를 함수 |
| --- | --- |
| `travelBegin()` | `tl.begin()`, `tl.setUserKey()`, `tl.setDefaultWalk()` |
| `travelLoop()` (`loop()`와, 태그 후 조회 한 건이 끝날 때마다) | `tl.loop()` |
| `travelOnDeparture(ev)` | `tl.notifyDeparture(user, stop, wx, tb, etaS, tempC)` |
| `travelGetSlackSec(...)` | `tl.slack(user, stop, wx, tb, etaS)`의 여유 시간 |

합칠 때 확인할 것

- 통신규격 5장에 따르면 출발 신호를 보내는 동안 `tl.loop()` 한 번이 최대 약 2.7초 걸릴 수 있다. 그동안 화면의 남은 시간 갱신과 서보 신호 끊기가 늦어질 수 있다.
- 반대로 API 조회 한 건(최대 8초) 동안은 `tl.loop()`가 불리지 않는다. 그 사이 폰의 요청은 응답 대기(5초)를 넘겨 시간 초과가 날 수 있고, 폰이 다시 보낸다. 조회와 조회 사이에는 `tl.loop()`를 부른다.
- `tl.loop()`는 스택을 많이 쓴다(위 "메인 스택"). 조회 함수 안쪽에서는 부르지 않는다.
- EEPROM 0~4095번지는 이동 시간 모듈이 쓴다. 메인 코드는 EEPROM을 쓰지 않는다.
- Wi-Fi 연결과 재연결은 메인 코드(`netBegin`, `netLoop`)가 한다. 모듈이 요구하는 조건과 같다. 재연결 뒤 모듈의 서버를 다시 열 필요는 없다(스케치 README의 "Wi-Fi 재연결").
- 사용자별 공유 키를 `secrets.h`에 추가해야 한다.
- 두 코드를 합친 상태의 RAM 사용량: 위 "RAM 사용량"에 다시 계산해 적었다(전역 변수 14,220바이트, 그중 모듈 3,640바이트). Arduino IDE로 컴파일해 같은지 확인한다.
